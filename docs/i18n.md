# Languages

The site is published in English, Brazilian Portuguese, Spanish, Hebrew, Japanese and Korean. English is the default and the fallback: a string that has no translation shows in English, so a missing translation never breaks a page.

| Language | URL | Direction |
|---|---|---|
| English | `/` | left to right |
| Português (Brasil) | `/pt-br/` | left to right |
| Español | `/es/` | left to right |
| עברית | `/he/` | right to left |
| 日本語 | `/ja/` | left to right |
| 한국어 | `/ko/` | left to right |

## How it is put together

| Piece | Where | What it does |
|---|---|---|
| Language list | `src/i18n/languages.json` | Code, native and English name, `lang`, direction, Open Graph locale, and which browser languages map to it. The pages, `astro.config.mjs` and the scripts all read this one file |
| Messages | `src/i18n/locales/<locale>/<namespace>.json` | One namespace per page (`home`, `install`, ...) plus `common` (nav, footer, buttons), `competitors`, `support` and `images` |
| Lookup | `src/i18n/index.ts` | `useI18n(Astro, 'install')` returns `t()`, `raw()`, `href()`, `date()`, `number()`. Locale values are merged over English key by key |
| Routes | `src/pages/[...locale]/` | Every page is one file that renders once per language through `getStaticPaths = localePaths` |
| Head tags | `src/layouts/Base.astro` | `lang`, `dir`, canonical, `hreflang` for every language plus `x-default`, `og:locale`, `inLanguage` in the structured data |
| Sitemap | `astro.config.mjs` | `@astrojs/sitemap` writes the `hreflang` alternates for every URL |
| Fonts | `src/styles/fonts-he.css`, `fonts-ja.css`, `fonts-ko.css` | Rubik and Heebo for Hebrew, Noto Sans JP for Japanese, Noto Sans KR for Korean, linked only on those languages. Other visitors never download them |
| Typography | end of `src/styles/global.css` | No negative tracking and more leading for Hebrew, Japanese and Korean; Japanese line breaking; Korean breaks between words only (`word-break: keep-all`); code stays left to right inside Hebrew |
| Images | `src/components/Figure.astro` | `<Figure name="security-boundary">` shows `src/assets/img/gen/<locale>/security-boundary.webp` if it exists, the English one otherwise |
| Checks | `npm run check:i18n` | Fails on a key English lacks, mismatched `{placeholders}`, HTML tags or `<code>` contents. Reports what still falls back to English. The deploy workflow runs it |

## How a visitor gets their language

1. **At Netlify's edge.** The build writes `dist/_redirects` with one rule per English page and language, such as `/install/  /pt-br/install/  302!  Language=pt`. Netlify matches the browser's `Accept-Language` header, so a Brazilian visitor who opens `aimemory.io/install/` lands on the Portuguese page without seeing the English one first.
2. **In the browser, as a fallback.** English pages carry a few lines of inline script that do the same thing with `navigator.languages`. This covers `npm run preview` and any host that is not Netlify.
3. **The visitor's choice wins.** Picking a language in the globe menu sets an `nf_lang` cookie for a year. Netlify's language rules read that cookie before the header, and the inline script does nothing when it is present. Someone with a Japanese browser who picks English stays in English.

Only a first visit to an English URL is redirected. A link to `/es/install/` always opens in Spanish, whatever the browser says. Search engine crawlers send no language header, get English at the bare URLs, and find the other languages through `hreflang`.

## Changing text

Every text change goes to all six languages in the same change. The check enforces it.

1. Edit the English string in `src/i18n/locales/en/<namespace>.json`.
2. Update the same key in the other five folders with a real translation. Translate the new meaning instead of patching a word into the old sentence. The rules and glossary are in `docs/research/I18N-TRANSLATE-BRIEF.md` and `docs/i18n/glossary-<locale>.md`.
3. `npm run i18n:stamp`, then `npm run check:i18n`.

Each language folder has a `.source.json` that records a fingerprint of the English text each translation was made from. When the English changes and a translation does not, `check:i18n` reports that key as STALE and fails, locally and in CI. `i18n:stamp` records the current English as translated, so run it only after the translations are really updated. `npm run i18n:stamp -- ja` stamps one language.

To add text, add the key to the English file first and use it in the page with `t('section.key')`. The other languages show the English text until someone translates it, and the check lists it as "falling back to English".

Rules the pages follow:

- No English in `.astro` files. Structure (hues, links, ids, commands) stays in code and words go in the catalog.
- One message per sentence. Never glue fragments together, because word order changes between languages.
- Variables are `{name}` placeholders: `t('hero.title', { tag })`.
- Inline markup stays inside the message and is rendered with `set:html`. Link targets are placeholders: `<a href="{href}">`.
- Internal links go through `href('/install/')`, which adds the language prefix.
- Commands, paths, flags, product names and numbers are never translated. In a code block only the `# comment` lines are.
- Dates and numbers use `date()` and `number()`.
- CSS uses logical properties (`margin-inline-start`, Tailwind `ms-`, `ps-`, `start-`), so Hebrew mirrors without extra rules. Arrows that mean "forward" carry `class="flip-rtl"`. Terminals, diagrams and file trees carry `dir="ltr"`.

The changelog on `/download/` is the project's own English text and stays in English in every language, with a note that says so.

## Adding a language

1. Add an entry to `src/i18n/languages.json`. Routes, redirects, `hreflang`, the sitemap and the language menus follow from it.
2. Copy `src/i18n/locales/en/` to the new folder and translate it. `docs/research/I18N-TRANSLATE-BRIEF.md` has the rules and a glossary; add a column for the new language.
3. If the script is not Latin, add a `fonts-<locale>.css`, link it in `Base.astro` next to the Hebrew, Japanese and Korean ones, and add a `:root:lang(xx)` font stack in `global.css`.
4. `npm run check:i18n && npm run build`, then look at the pages.

## Images with text

The diagrams are pictures, so their labels are translated by editing the English image: the artwork stays identical and only the words change.

```bash
export GEMINI_API_KEY=...
node scripts/localize-image.mjs how-it-works ja      # one image
node scripts/localize-image.mjs --all pt-br          # every image that has labels
```

The labels live in the `images` namespace like any other text: `src/i18n/locales/en/images.json` lists each image's translatable labels, and the same file in each language folder holds the translations. The script sends the English image and the label pairs to Gemini and writes `src/assets/img/gen/<locale>/<name>.webp` at the same pixel size. `Figure` picks it up with no change to the page.

Always open the result and compare each label with `images.json`, character by character. Hebrew, Japanese and Korean are where a model is most likely to drop or swap a character. In Hebrew, a label that starts with a Latin word ("LAN עם TLS") tends to come out in the wrong order, so word such labels to start in Hebrew ("רשת מקומית עם TLS"). If a label is wrong, run it again. If it keeps failing, delete the file and that language shows the English diagram.

When you regenerate an English diagram with `scripts/gen-image.mjs`, delete its translated copies and run `localize-image.mjs` again, or the languages will show the old drawing.
